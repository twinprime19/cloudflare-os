# Workspace idle pause

An open workspace tab keeps its Overseer Durable Object (and the user's UserDurableObject) in memory through the live RPC WebSocket, and idle tabs were 94% of billed DO duration. The frontend closes that socket on purpose when nobody is using the tab, then reconnects through the ordinary outage path. The Worker backs it up: a socket that has carried no inbound frame for 30 minutes is closed server-side with WebSocket code 4001 (`SESSION_IDLE_CLOSE_CODE` / `SESSION_IDLE_CLOSE_MS` in `workshop-shared/src/api.ts`, `attachIdleClose` in `server.ts`), which releases every Durable Object stub behind it.

**What pauses.** The whole RPC socket, for the workspace route (`/workspace/<id>`; `/gadget/<id>` redirects there), never individual stubs. The home page is not covered. The Worker session ends, every DO stub behind it is released, and the Overseer and User DOs go idle within their normal grace period. Calls issued while paused queue on the placeholder stub and flush on resume, so chat history, the composer draft, and the gadget iframe (with its in-frame state) all survive.

**Thresholds.** Hidden tab: 5 minutes. Visible tab with no input: 15 minutes. Mouse movement is not input; clicks, keys, touch, wheel, and scroll defer the pause in the page; inside the gadget iframe the sandbox bootstrap forwards clicks, keys, touch, and wheel to the parent as an `activity` message (at most one per 10 seconds), which covers scrolling by trackpad, scrollbar, keys, or touch. A focused but untouched iframe is idle. No pause while the selected chat is streaming or the server is waiting on a client-hosted observer callback. Constants live in `packages/workshop-frontend/src/useWorkspaceIdle.ts`; the pause flag and reconnect parking live in `connectionPause.ts`, hooked into `main.tsx` and `GadgetUI.tsx`.

**Resume is deliberate.** Nothing wakes a paused workspace by itself: not the tab becoming visible, not clicking around, not typing. Reading what is already on screen costs nothing, and a revived Durable Object stays awake until the next threshold. What resumes: sending from the composer (the message goes out after the reconnect), approving or denying an action or connection request, clicking the Paused chip, or leaving the workspace. Anything else done while paused (a gadget button, a code edit, opening another gadget view) queues until one of those happens; the chip is the hint, and it is present on the use-only view too.

**What the user sees.** While paused, the top-bar chip reads "Paused — click to reconnect" and is a button. The usual "Reconnecting…" chip appears only during the resume itself.

**Verifying on staging.** Query `durableObjectsPeriodicGroups` with dimensions `namespaceId, objectId` (objectId equals the `<id>` in the workspace URL) and sum `duration, activeTime, subrequests, inboundWebsocketMsgCount`. A paused workspace's `activeTime` flatlines within about two minutes; the user's UserDurableObject too. Full query: `plans/reports/durable-objects-cost-consult-260904-1306-do-billing-attribution-report.md`.

**Server idle close.** A tab whose JavaScript is not running (Edge sleeping tabs, Chrome memory saver, a laptop asleep with the workspace visible) never reaches a threshold, and a session can hold stubs the tab no longer shows. The Worker's 30-minute inbound-idle close covers those. When the client sees code 4001 on a workspace route, it parks exactly as if its own threshold had fired (not busy, no input for 15 minutes; the tab becoming visible is not input here, so a thawed frozen tab parks instead of dialing) and shows the Paused chip; a tab that is busy or whose user is still typing or clicking in the gadget reconnects at once, and so does the home page, which has no pause. Other close codes take the ordinary outage path.
