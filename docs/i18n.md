# i18n

`packages/workshop-frontend` is fully wrapped in Lingui v6 macros. English lives inline in source as
the message source — there is no separate "extract strings to JSON" step in your head, `lingui
extract` does that mechanically from what you write. Translation (Vietnamese first) is catalog-only:
drop a `.po` file in, zero source changes, per the design in
`plans/reports/brainstorm-260818-1401-i18n-frontend-string-extraction-report.md`.

Scope: **frontend only** (`packages/workshop-frontend`). Backend, gatekeeper strings, LLM prompt
text, blueprint/gadget content are out of scope — see [Known gaps](#known-gaps-and-deferred-work).

The full worked-example spec used for this extraction is
`plans/260818-1401-i18n-frontend-string-extraction/extraction-conventions.md` (~1,040 lines, 17
worked examples, every rule below distilled from it). This doc is the load-bearing summary; read the
conventions doc when a real edit doesn't match one of the shapes here.

## Where things live

| Path | What |

| `packages/workshop-frontend/vite.config.ts` | wires the Babel macro plugin into `react()` and adds `@lingui/vite-plugin`, both resolved against `packages/i18n`'s config via `getConfig({ cwd: … })` from `@lingui/conf` — a plugin-order-sensitive block worth reading in full if a sync conflicts here |

| `scripts/i18n-codemod/unlocalized-allowlist.txt` | intentional exceptions (dead code, backend-mirrored text, RPC-boundary errors) |

Components import Lingui macros directly (`@lingui/react/macro`, `@lingui/core/macro`), not through
`@gadgets/i18n` — that package owns configuration and the provider only. This is deliberate: it's the
shape upstream would use if it ever adopted i18n itself, so wraps inside component files don't gain
an extra layer of indirection that has to be re-justified on every sync.

## Writing a new user-facing string

Four forms. Pick by where the text lives, not by habit.

### `<Trans>` — JSX children

```tsx
import { Trans } from '@lingui/react/macro'

<p><Trans>Delete workspace?</Trans></p>
<p><Trans>Shared by {gadget.owner.name}</Trans></p>
```

Everything inside `<Trans>` becomes **one message**: text, `{expressions}` (→ placeholders), and
nested elements (→ `<0>`, `<1>` tags). An expression that is a simple identifier keeps its name in
the catalog (`{actionLabel}`); a property access or call becomes numbered (`{0}`) with a `#.
placeholder` comment for the translator. Both are fine — never extract an expression into a new
`const` just to get a prettier placeholder name (that's a code change, not a wrap).

### `` t`…` `` — attribute values and plain strings

```tsx
import { t } from '@lingui/core/macro'

<input placeholder={t`Search blueprints…`} />
throw new Error(t`Invalid image dimensions.`)
toasts.add({ title: t`Failed to enable auto-approval`, variant: 'error' })
```

This is the **core** macro on the global `i18n` instance mounted at `main.tsx`. No hook, no provider
lookup — it works identically in a `.tsx` component and a plain `.ts` helper module (toast builders,
validation errors), as long as the string is built inside a function body that runs at call time, not
at module load (see [module-scope constants](#module-scope-constants-need-msg-not-t) below).

### `plural()` — function-call form, composes inside `t`

For counts outside JSX (imperative DOM building, a `string`-typed value that can't hold JSX):

```ts
import { plural, t } from '@lingui/core/macro'

button.textContent = plural(hidden, {
  one: 'Show # hidden deleted line',
  other: 'Show # hidden deleted lines',
})

// composes inside a t-template when the count sits mid-sentence and the result must stay a string:
t`You created ${plural(createdGadgets.length, { one: "gadget", other: "gadgets" })} ${createdTitles}`
```

`#` substitutes the count value. English needs exactly `one` and `other` — never add `zero`, `few`,
`many`. Real precedent for the composed form: `ChatInterface.tsx`, which also holds a local
`pluralize` helper. **Never alias a macro import** (`plural`, `t`, `msg`, `Trans`) — `detect.ts`
recognises a localizing call by callee name, so an aliased `plural` is invisible to the guard and its
`one`/`other` strings get reported as unlocalized. On a collision with a local binding, rename the
local instead: `pluralize`'s third parameter is `pluralForm`, a one-line divergence from upstream
re-applied on every sync.

### `<Plural>` — JSX form, can nest inside `<Trans>`

```tsx
import { Plural } from '@lingui/react/macro'

<Plural value={vendor.resources.length} one="# resource hidden" other="# resources hidden" />

// nested inside a longer sentence:
<Trans>
  {usage.remaining} of{' '}
  <Plural value={usage.dailyLimit} one="# request" other="# requests" /> remaining today
</Trans>
```

**Only convert to `<Plural>` when the source already contains manual singular/plural logic**
(`? '' : 's'`, `? 'row' : 'rows'`). A bare count with no existing plural branch renders the same
wrong output today and tomorrow (`1 rows in channels`) — "fixing" it during a wrap is an unauthorized
copy change. **Put only the words that vary by count inside `one`/`other`**; if the count sits inside
a longer sentence with another interpolated value, nest `<Plural>` inside `<Trans>` rather than
writing the whole sentence twice in a template-literal prop — Lingui numbers each template-literal
expression independently, so the same variable would get two different placeholder numbers in the
catalog (verified in `extraction-conventions.md` §5 E8).

Full worked set (17 examples, every edge case: conditionals, concatenation, name-slot fallbacks,
attribute escapes, mixed markup): `plans/260818-1401-i18n-frontend-string-extraction/extraction-conventions.md` §5–§6.

## The cardinal rule

**A sentence a user reads as one sentence must be one message, with placeholders for the parts that
vary. Never split it into two or three messages.**

```tsx
// WRONG — "Shared by" is a dangling, untranslatable fragment
<p><Trans>Shared by</Trans> {gadget.owner.name}</p>

// RIGHT — one message, one placeholder
<p><Trans>Shared by {gadget.owner.name}</Trans></p>
```

A translator receives a flat list of `msgid`s with no surrounding code. A fragment like `"Shared by"`
depends on word order, case ending, and preposition choice in the target language — none of which the
translator controls if the sentence arrives pre-chopped. The mechanical test: **if you can read the
pieces aloud as one sentence, they are one message.**

**No automated gate can detect a fragment.** A split sentence renders identical English, passes
`tsc`, passes the frontend test suite, and passes the guard (`check-unlocalized-strings.ts`) — the
guard only knows "is this text wrapped by something," not "is this text a complete thought." Two real
fragments shipped in this wave and were caught only by a human reading the extracted catalog
end-to-end, not by any tool:

- `routes/providers.tsx` — `Quick model:` and `none set.` extracted as two separate messages instead
  of one label+value message.
- `WorkpiecePicker.tsx` — a leading `·` separator sat inside a message that should have carried it
  outside.

Both are fixed now, but the lesson is the point: **reviewing i18n work means reading the msgids in
`packages/i18n/locales/en.po`, not the source diff.** A diff shows you a wrap was added; it does not
show you whether the wrap boundary is a sentence or a piece of one. Skim the catalog for anything that
starts lowercase, ends mid-clause, or reads like a UI label fragment (`"Shared by"`, `"and"`, a bare
verb) before calling a wrapping pass done.

## Commands

| Command | What it does |
|---|---|
| `pnpm i18n:extract` | runs `lingui extract --clean` scoped to `packages/i18n/lingui.config.ts`; regenerates `packages/i18n/locales/*.po` |
| `node scripts/check-unlocalized-strings.ts` | the guard — scans `packages/workshop-frontend/src` for JSX text, whitelisted attributes, JSX expression containers, and `.ts` string literals that no macro wraps yet. Exit 1 if anything is found. `--dir <path>` scopes it; `--json` for machine output; `--helper-literals` additionally reports non-JSX `.tsx` literals (variables/record properties — see [gaps](#known-gaps-and-deferred-work)) |
| `node scripts/i18n-codemod/run.ts --dry-run --report out.json` | mechanical codemod, dry run — plans wraps + emits a residue report of what it refuses to guess at |
| `node scripts/i18n-codemod/run.ts --apply` | applies the mechanical wraps for real. Idempotent — a second run against an already-wrapped tree plans zero edits |
| `pnpm i18n:check` (`node scripts/check-i18n.ts`) | the CI-equivalent gate — three independent checks, below |

`pnpm run lint` is `lint:check && types:scripts && i18n:check && types:check` (`package.json` root) —
`i18n:check` runs before `types:check` (the build) deliberately, so a stale catalog fails before the
slow step. Adds **~1.4s** to a warm `lint` run (measured: 4.8–5.3s without it, 6.3–6.5s with it;
`i18n:check` alone runs 1.5–1.7s, mostly `lingui extract` and the detector).

`scripts/check-i18n.ts` does three things, none of which any other check in the repo would catch:

1. **Catalog freshness — decided by hashing, not `git diff`.** SHA-256 every `.po` under
   `packages/i18n`, run `pnpm i18n:extract` (which mutates the catalogs in place), hash again, compare.
   Anything added, removed, or changed fails, and the message says review-and-commit rather than
   "run something else" — the extract already corrected the file on disk.
   **Why hashing and not `git diff --exit-code`:** `git diff --exit-code` is the obvious
   implementation and is unsound on this tree. `git diff` reports on tracked paths only, and
   `packages/i18n/` is untracked — so appending a garbage line to `en.po` and running `git diff
   --exit-code` on it returns **0**, no matter how far the catalog has drifted. That's a check that
   looks like coverage and provides none. Hashing doesn't care whether git has ever heard of the file,
   so it holds identically on an untracked working tree, a fresh clone, and in CI. A catalog **absent**
   before the extract also fails (not passes) — that's the fresh-clone / never-committed case, caught
   without any git call at all.
2. **Locale configuration** — every catalog under `packages/i18n/locales` must have its locale listed
   in `locales: [...]` in `lingui.config.ts`. This is not a style nit; see [Future locale
   switching](#future-locale-switching) for the silent failure it guards against.
3. **Bare strings** — spawns `scripts/check-unlocalized-strings.ts` unchanged and propagates its exit
   code. No detection rule is duplicated between the two scripts.

Git is still consulted, but only for two things hashing structurally cannot see, both about whether
the freshness comparison will keep meaning anything tomorrow rather than about today's contents:

- **A catalog git *ignores* is a fatal failure.** An ignored file can never be committed, so every
  clone and every CI run would start without it — the check would only ever be inspecting a file it
  had just regenerated, forever green, forever meaningless.
- **A catalog that is merely *untracked*** (today's state, this whole package's first commit hasn't
  happened yet) **prints a loud, non-fatal note** — hashing already proved freshness regardless, so
  failing here would only turn `pnpm lint` red on the current tree for zero extra verification. The
  note states explicitly that hashing, not git, did the verifying, and that a `git diff`-based check
  would have passed here regardless of contents.

Five empirical proofs are in
`plans/reports/from-fullstack-developer-to-orchestrator-260819-1045-i18n-phase05-verification-report.md`
§1: a deliberately staled catalog (exit 1), a catalog absent entirely (exit 1), a planted bare string
(exit 1), a git-ignored catalog (exit 1), and a clean tree (exit 0). `scripts/check-i18n.test.ts` adds
22 colocated unit tests.

## The untracked-catalog trap

As of this writing, `packages/i18n/` — including `locales/en.po`, the whole catalog — is
**untracked** in git (`git status` shows `?? packages/i18n/`). Whether to commit it is **the user's
decision, still open** as of this writing. Two consequences follow from leaving it untracked:

1. **The catalog is lost if it isn't committed with the rest of the wave.** Hundreds of messages,
   none reconstructible without re-running extraction from source. This is true regardless of any
   tooling — it's a plain "uncommitted work vanishes" fact.
2. **A `git diff --exit-code`-based freshness check would pass green regardless of drift**, because
   `git diff` reports on tracked paths only. If you're ever tempted to write a check like that
   yourself (for this catalog or another untracked generated file), don't — see how
   `scripts/check-i18n.ts` gets around it below.

**`i18n:check`, as shipped, does not have problem 2** — it decides freshness by hashing the catalog
before and after a real extraction, which doesn't care whether git has ever heard of the file (see
[Commands](#commands)). So the gate is real today, on this untracked tree, exactly as it will be after
a commit. What hashing can't fix is problem 1: a catalog that's never committed is still a catalog
that's lost, no matter how well the freshness check works in the meantime. **Whoever decides to land
this work still needs to commit `packages/i18n/` (including `locales/en.po`)** — the check protects
against drift, not against the file never reaching the remote at all.

## Future locale switching

**"Zero source changes" means zero *component* changes, not literally zero.** Adding a language
requires three registration lines, all inside `packages/i18n`, and genuinely zero edits under
`packages/workshop-frontend/src`:

1. Drop `packages/i18n/locales/xx.po` in.
2. Add `'xx'` to `locales` in `packages/i18n/lingui.config.ts`. **Not optional, and silent when
   omitted** — see the failure this step exists to prevent, below.
3. Add `'xx'` to `SUPPORTED_LOCALES` in `packages/i18n/src/index.tsx`, so `Locale` admits it and
   `detectLocale()` can return it (currently a stub returning `SOURCE_LOCALE` — there's nothing for a
   browser-language check to select between while English is the only catalog).

The plan's acceptance criterion is worded "adding a Vietnamese catalog later requires zero source
changes," and it's **deliberately left unticked** for exactly this reason — as literally worded, it's
contradicted by step 2 above. "Zero component source changes" is what's actually true and proven (a
real, pre-existing, untouched component — `components/ReconnectingChip.tsx` — was verified flipping
locale with no edit to it at all). Rewording the criterion is a call for whoever owns the plan, not
something this doc can do on its own authority.

### Step 2 is not optional — the silent failure it prevents

The first attempt at proving this pipeline **failed**, and the failure is the most consequential
finding of the whole effort. Drop a `.po` file into `packages/i18n/locales/` for a locale that
`lingui.config.ts`'s `locales` array doesn't list, and:

- The import still succeeds.
- The module still exports the full set of message ids.
- `i18n.locale` still reports the new locale as active.
- **Every string on screen still renders in English.**

Nothing throws. Nothing logs. `lingui extract --clean` does not clean up or remove the orphaned
catalog either — it has no opinion about a `.po` file it wasn't told to compile translations from.
Cause: `@lingui/vite-plugin` compiles a `.po` whose locale is absent from `locales` **from the source
language**, not from that file's own `msgstr` values. The only symptom is a translation that silently
never appears, which reads as a bad catalog file, not as one missing line of config — there is nothing
to grep for and nothing in the console to point you at it.

`packages/i18n/src/index.tsx` used to assert, in its own docstring, that dropping a catalog in was
"the whole change." That claim was wrong and has been corrected in code — the comment now lives on
`SUPPORTED_LOCALES` and states the full three-step recipe plus this failure mode. `i18n:check` now
catches the omission directly (its "locale configuration" check, [above](#commands)) — proof E in the
phase-5 verification report demonstrates the exact failure and the exact fix, with the check's error
message naming both the missing config line and the follow-up `SUPPORTED_LOCALES` line.

Once both config lines are present, `loadCatalog()`'s **template-literal dynamic import** —
`` await import(`../locales/${locale}.po`) ``, which Vite turns into a glob over
`packages/i18n/locales/` — needs no vite change and no component change to pick up the new file.

**A brand-new catalog file must be extracted twice before committing.** The first `lingui extract`
against an empty/missing catalog creates it and, on that first run only, `@lingui/format-po`'s
`parsePo`/`createPoFile` round-trip adds the standard empty PO headers (`Project-Id-Version`,
`PO-Revision-Date`, `Last-Translator`, …) that don't exist on a from-scratch file. Run extract again
and it's byte-identical from then on. Skip this and the committed catalog will differ from a fresh
extract on the very next CI run, tripping `i18n:check` for no real reason.

**Why the source locale (`en`) is loaded differently from every other locale.** In
`packages/i18n/src/index.tsx`, `en.po` is a **static** import at module scope, activated before any
component renders. Every other locale is **lazy** — fetched via the dynamic `import()` above, inside
an effect, only once `AppI18nProvider` mounts with a non-source `locale` prop. This isn't an
optimization; reversing it silently breaks placeholders in production:

`@lingui/core` registers its runtime ICU compiler only when `NODE_ENV !== 'production'`. This
project's Babel config uses `descriptorFields: 'message'`, which embeds each message's raw ICU source
text at its call site as an inline fallback (so a forgotten `lingui extract` can never blank the UI —
see [Accepted deliberate behaviors](#accepted-deliberate-behaviors)). But that inline text is
**uncompiled** ICU. If a message resolves through the inline fallback instead of a compiled catalog in
a production build, a plain string renders fine but a message with a placeholder or plural renders its
ICU source **verbatim** — `Always approve "{actionLabel}"?` reaches the user with the braces still in
it. Loading the source catalog eagerly and synchronously closes that hole for `en`; a component never
has a tick where it renders before the compiled English catalog is active. A future locale can afford
to be lazy because a failed or in-flight fetch for it falls back to the (already-active, already
compiled) English — degrading to correct English, never to raw ICU or a blank screen. Two test files
pin this behavior: `packages/workshop-frontend/src/i18nCatalog.test.ts` (production-semantics message
resolution — proven to fail on the pre-fix code) and `i18nProvider.test.tsx` (build-wiring/render
smoke). **Never make the source-locale catalog lazy.**

## Architecture patterns

### Module-scope constants need `msg`, not `` t`…` ``

A `const` object or array declared at module scope is evaluated once, at import time — before
`AppI18nProvider` has activated a locale. Wrapping a string inside it with `` t`…` `` freezes that
string at whichever locale happened to be active (or none) the moment the module first loaded, and it
never updates on a later locale switch.

The fix: `msg` captures the source text and message id at **compile time** with no runtime locale
dependency (it does not resolve to a string). Resolve it at **read time** with `i18n._()`, inside a
getter or a function — real code from `components/format/formats.ts`:

```ts
import { msg } from '@lingui/core/macro'
import { i18n } from '@gadgets/i18n'

// Message descriptors, not resolved strings — GENERIC_OUTPUT is a module-scope constant evaluated
// once at import time, before the active locale is guaranteed to be set. `msg` only captures the
// source text and message id at compile time. Resolution happens in the getters below, at read time.
const GENERIC_OUTPUT_NOUN = msg`App`
const GENERIC_OUTPUT_PLURAL = msg`Apps`

export const GENERIC_OUTPUT: BlueprintOutput = {
  id: 'app',
  get noun() {
    return i18n._(GENERIC_OUTPUT_NOUN)
  },
  get plural() {
    return i18n._(GENERIC_OUTPUT_PLURAL)
  },
  icon: 'appWindow',
}
```

A getter is transparent to every consumer typed against `BlueprintOutput` — `GENERIC_OUTPUT.noun`
still reads as a plain `string`, re-evaluated fresh on every access, and a `{ ...GENERIC_OUTPUT, icon }`
spread still works (it invokes the getters once and copies their resolved values). No consumer file
needs to change. **Never** evaluate `` t`…` `` at module scope — it runs once, at import time, and
never again.

### A value that doubles as a type discriminant must never be translated

`packages/workshop-frontend/src/diff/diffModel.ts`'s `DiffStatus` (`'Added' | 'Deleted' | 'Modified' |
'Unchanged'`) is compared and switched on elsewhere (`model.status !== 'Modified'` gates rendering in
`CodeDiffEditor.tsx`) **and** was, before this fix, rendered verbatim as badge text. Wrapping the
literal in place would either break every comparison against it or require threading a second,
parallel "display" field through every call site that builds one.

The fix: leave the discriminant's values as plain English identifiers, and map identifier → label at
the render site instead:

```ts
import type { MessageDescriptor } from '@lingui/core'
import { msg } from '@lingui/core/macro'
import { i18n } from '@gadgets/i18n'

export type DiffStatus = 'Added' | 'Deleted' | 'Modified' | 'Unchanged'

const DIFF_STATUS_LABELS: Record<DiffStatus, MessageDescriptor> = {
  Added: msg`Added`,
  Deleted: msg`Deleted`,
  Modified: msg`Modified`,
  Unchanged: msg`Unchanged`,
}

/** Translated display text for a DiffStatus. Resolves against the active locale at call time. */
export function diffStatusLabel(status: DiffStatus): string {
  return i18n._(DIFF_STATUS_LABELS[status])
}
```

`buildDiffModel`'s return statements (`status: 'Added'`, …) are untouched — the discriminant stays
these exact English strings forever, allowlisted in `unlocalized-allowlist.txt` with a reason pointing
at `diffStatusLabel`. `CodeDiffEditor.tsx` calls `diffStatusLabel(model.status)` at the render site,
never `{model.status}` directly. The same rule applies to any RPC-value, `===`-compared, or
React-`key` string — see the "never wrap these" table in `extraction-conventions.md` §7.1
(`gk.name`, `binding.gatekeeperName`, error `code` values).

## Accepted deliberate behaviors

Written down so a future audit doesn't re-litigate them as bugs.

- **ICU `#` applies `Intl.NumberFormat`.** Every `<Plural>`/`plural()` in the app renders `n ≥ 1000`
  with a thousands separator — `1,000` — where the pre-extraction template rendered `1000` with no
  formatting. This is the **single intentional rendering change** in this entire effort; every other
  wrap was verified byte-identical to the prior output across the full state space it could reach.
  Affects every plural in the app, not one call site.
- **`descriptorFields: 'message'` keeps inline English as the fallback**, rather than the v6 default
  (`'auto'` → id-only in production). The v6 default would render every wrapped string as a bare hash
  unless a matching compiled catalog happens to load with matching ids — this way a forgotten `lingui
  extract` degrades to correct English instead of blanking the UI. See [locale
  switching](#future-locale-switching) above for the corollary this creates (source catalog must be
  eager, not lazy).
- **Nested `` t`…` `` inside a `??`/`||` fallback is verified-correct**, not a fragment, even though it
  *looks* like one to a scan for lowercase standalone `msgid`s. Real instances: `latestAuthor?.name ??
  t\`The agent\``, `attachment.name ?? t\`attached file\``, `sk.note || t\`share link\``
  (`ShareModal.tsx`), `resourceTitle ?? t\`connection\`` (`AccountChooser.tsx`). These occupy a
  **name slot** in a larger sentence — `"The agent"` is not a piece of that sentence's grammar, it's a
  fallback value standing in for a person's name, exactly like the runtime name it substitutes for. It
  gets its own message because it's semantically a value, not because it was hard to wrap otherwise.
  All four were verified through the real Babel macro plugin, not just read. A future audit scanning
  the catalog for lowercase-starting `msgid`s (a reasonable heuristic — see the [cardinal
  rule](#the-cardinal-rule) section on reviewing by catalog) will flag these; check whether the msgid
  is a name-slot fallback before treating it as a defect.

## Upstream-sync playbook

The fork-wide reconciliation rules (who wins on which surface, test policy, recurring traps) are in
[`upstream-sync-decisions.md`](./upstream-sync-decisions.md); this section is the i18n-specific mechanics.

This fork tracks a very active upstream (97 commits in the 14 days before this extraction shipped)
that has no i18n of its own — a conflict on a wrapped line is routine, not exceptional, and will
recur on every sync from now on.

`packages/i18n/` is purely additive (a new package upstream doesn't touch), so it can never conflict.
The entire conflict surface is the `<Trans>`/`` t`…` ``/`<Plural>`/`plural()` wraps inside
`packages/workshop-frontend/src`. `lingui.config.ts` also sets `origins: false` specifically to keep
this cheap — the catalog carries no `#: file.tsx:line` comments, so a wrapped line moving up or down
doesn't itself produce a catalog diff; only a changed `msgid` does.

On a conflict at a wrapped line:

1. **Take upstream's copy of the English text.** Don't try to hand-merge the wrap into upstream's new
   wording — resolve the conflict in favor of upstream's source text first, unwrapped if that's
   simpler, then re-wrap.
2. **Re-wrap mechanically first:** `node scripts/i18n-codemod/run.ts --apply` against the touched
   file(s). It's idempotent and handles the same mechanical majority it handled in the original pass
   (~88% of strings, by the numbers from this round).
3. **Run the guard** (`node scripts/check-unlocalized-strings.ts --dir <touched path>`) for whatever
   the codemod refused. Anything left needs a human or model applying
   `extraction-conventions.md`'s rules — same process as the original residue wave, just per-conflict
   instead of per-file-shard. **Remember the guard cannot see fragments** — re-read the cardinal rule
   section before resolving anything that looks like a sentence built from pieces.
   A file upstream added wholesale is the same problem without a conflict, so run the guard over it
   too. Much of what it finds there isn't UI copy at all — backend failure text matched with
   `.includes()`, CSS values handed to an API that parses them as CSS — and that gets an entry in
   `scripts/i18n-codemod/unlocalized-allowlist.txt` with a reason, not a wrap (precedents:
   `otClient.ts`'s retryable-error needles, `components/codeTheme.ts`'s editor theme values).
4. **Re-extract:** `pnpm i18n:extract`, then run it a second time and confirm no further diff (the
   determinism check this whole pipeline relies on).
5. **A changed English sentence correctly becomes a new untranslated catalog entry.** This is expected
   behavior, not a defect — if upstream changed the wording, the old translation (once one exists) no
   longer applies to it, and the new `msgid` starts out untranslated until someone updates it.
6. Run the normal gates: `pnpm -C packages/workshop-frontend exec tsc`, `pnpm -C
   packages/workshop-frontend run test:run`, `pnpm exec vp lint`. A test upstream added that mounts a
   component subtree fails until its root comes from `createI18nRoot()` (`src/testI18nRoot.tsx`)
   rather than `createRoot` — `<Trans>` reads the provider from context, and `` t`…` `` needs a
   locale someone activated.

## What's out of scope here

- **Backend adoption.** `@gadgets/i18n`'s catalog config supports multiple `catalogs[]` entries in one
  config — backend adoption later is a second catalog entry, not a second Lingui config. No work has
  been done on this; it needs its own plan when it's needed.
- **Actual translations.** This round proves the pipeline (Lingui extraction, catalog loading, locale
  switching) works end to end without producing a single translated string. Vietnamese (or any other
  locale) is a future, separately-scoped effort — see [Future locale switching](#future-locale-switching)
  for what that effort will and won't need to touch.
- **A visible locale switcher UI.** `detectLocale()` is a stub; there's no UI for a user to pick a
  language yet. Out of scope per the brainstorm's approved boundaries.
