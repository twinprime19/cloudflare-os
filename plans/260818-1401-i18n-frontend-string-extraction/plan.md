# i18n core + frontend English string extraction (Lingui v6)

## Overview

Extract all user-facing English strings in `packages/workshop-frontend` into a Lingui v6 i18n layer so future translation (Vietnamese first) is catalog-only — no component changes, and three registration lines inside `packages/i18n` per locale. English stays inline in source as the message source (`<Trans>`, `` t`...` ``); catalogs are generated by `lingui extract`, never hand-edited. Architecture chosen to minimize merge-conflict cost against very active upstream (97 commits/14 days; i18n never mentioned upstream — fork-local divergence).

Design authority: `plans/reports/brainstorm-260818-1401-i18n-frontend-string-extraction-report.md` (user-approved 2026-08-18). Scope: frontend only. Out: backend/gatekeeper strings, LLM prompts, blueprint/gadget content, translations, locale switcher.

Execution cost model (user constraint): core + codemod built by high-quality model; mass extraction residue by cheapest-model swarm; deterministic tooling preferred over LLM wherever possible.

### Phase 5 finding: the translation path has a silent failure mode

Measured with a throwaway pseudo-locale (machine-mangled English, `[!! … !!]`), now deleted. With
`locales/pseudo.po` present but `pseudo` absent from `locales` in `lingui.config.ts`,
`@lingui/vite-plugin` compiles the catalog **from the source language**: the import succeeds, the
module exports all 809 message ids, `i18n.locale` reports `pseudo`, and every string on screen is
still English. Nothing throws and nothing logs. The symptom reads as a bad translation file rather
than as a missing line of config.

With that one config line added, an unmodified app component (`components/ReconnectingChip.tsx`)
rendered `[!! Reconnecting… !!]`, and an interpolated message rendered
`[!! Always approve “Delete file”? !!]` with the placeholder still substituted. Zero component
source changes, as designed.

`pnpm i18n:check` now fails on a catalog whose locale is unconfigured, so that state cannot reach a
browser, and `SUPPORTED_LOCALES` in `packages/i18n/src/index.tsx` documents the three-line recipe.

### Accepted deliberate behaviors — do not re-litigate

- ICU `#` applies `Intl.NumberFormat`, so n ≥ 1000 renders `1,000` where the old code rendered `1000`.
  This is the **only** intentional rendering change in the entire effort.
- `descriptorFields: 'message'` keeps inline English as the production fallback.
- Nested `t` inside `??` fallbacks (`attached file`, `connection`, `share link`) is verified correct
  and will *look* like fragments to a future audit. It is not.

### The one thing a successor must internalize

**No automated gate in this pipeline can detect a sentence fragment**, a reordered clause, or a lost
space — all render identical English and pass typecheck, tests, and the guard. Two real fragments
were introduced during this work and were caught only by reading the extracted msgids in `en.po`.
Reviewing i18n work means reading the catalog, not the source diff.
